# ロスから仕掛への復活機能

## 導入順序
1. Supabase SQL Editorで `supabase/migrations/restore_loss.sql` の全文を実行する。
2. 成功後、このフォルダのアプリを通常の手順でビルド・デプロイする。
3. ブラウザを再読み込みする。

SQLは既存データのロス数を一括変更しない。操作した対象だけを更新する。既存の工程有効フラグ・支払明細の状態/伝票日付/納入ID列がある現行環境向け。初期化SQLやschema.sqlの再実行は不要。
本番DBとホスティングへの反映は、この納品では行っていない。

## 使い方
工程実績・納入でロットと工程・外注先を選び、「ロスから戻す」の数量を入力して確認する。初期値はロス全数。一部だけ戻すこともできる。
完了ロットはロスが残っている場合に復活専用で選択できる。取消済みロット・受注、無効工程は対象外。
工程編集権限が必要。外注先未設定、適用単価が未設定/重複の場合は理由を表示し、変更を取り消す。

## 更新される値
- 工程：ロス減算、現在数増加、仕掛中へ変更。投入数・完了数は維持。
- ロット：仕掛中。受注は未出荷が残る場合のみ仕掛中へ戻し、全数出荷済みは完了維持。
- 支払：復活数量の仕掛明細を追加。工程個別単価を優先し、なければ当日有効なマスタ単価。0円も有効。伝票日付・対象月は日本時間の復活日。
- 履歴：`loss_restoration_history` に数量・配分・単価・操作者・日時・request_idを保存。新規納入としては計上しない。
- 在庫・出荷・納入数量と既存の支払予定/支払済/確認済明細は復活操作で変更しない。

支払管理の日時表示は日本時間に合わせ、月初直後の復活明細が既存の当月フィルターから漏れないようにした。ロット一覧の数量参照も実DB項目へ整合させた。レイアウトは維持。

## 同時操作と整合性
復活は一つのDBトランザクション。途中エラー時は全変更を戻す。同一request_idの再送は同じ結果を返し、二重加算しない。
既存のロス確定も原子化し、復活処理と共通の行ロック順で処理する。共有する仕掛支払の追加・消費・編集はDB内の差分更新に移し、古い合計金額で復活分を上書きしない。
復活したロットでは、現在数が残っているのに古い画面から完了状態へ更新する操作を補正する。ダッシュボードの既存編集権限を維持し、復活とロス確定は工程編集権限に限定。
